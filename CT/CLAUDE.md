## 作業のルール（ユーザーとの約束）

- **やり取りはすべて日本語**。返事の本文だけでなく、作業の終わりの要約・確認の質問・選択肢のボタン・作業の一覧の項目も日本語で書く。

- **1つ作り終えるたびに、コミットメッセージ（日本語）を作って渡す。** 複数まとめて頼まれたら、最後にまとめて1つ。
- **コミットメッセージは毎回「前回のコミットからの差分すべて」で書く**（ユーザーの指示、2026-11-13）。`changes.ps1` で最後のコミットと未コミットの変更を見て、まだコミットされていない作業（前の依頼の分も含む）を1つのメッセージにまとめる。今回の作業の分だけで書かない。
- **ほかの人が書いたコードを変えたときは、コミットメッセージにその人への説明を書く**（どのファイルの何を・なぜ変えたか・その人の作業への影響）。書いた人はファイル先頭の `\author`、または Git の履歴（`changes.ps1` / `git log -- <ファイル>`）で確かめる。私（uh）以外が書いた部分が対象。
- **コミット・push はユーザーが自分で行う**（Fork を使っている）。こちらからは commit / push しない。**変更する Git の操作（commit・push・ブランチの切り替え・stash・reset など）は頼まれたときだけ行う。**読むだけの操作（status・diff・log）はいつでもしてよい。
- プランナー向けの機能には、**Inspector の項目名・Tooltip を日本語で付け**、`Docs/` に手順書を書く（または追記する）。
- 実装したら、**Unity CLI で実際のエディタを操作して動作確認する**。確認できなかった項目ははっきり伝える。
- 既存のコードの問題を見つけたら、勝手に直さずに報告する（頼まれたら直す）。そして `Docs/code-map.md` の問題点に追記する。
- 作業が終わったら、CLAUDE.md・`Docs/code-map.md`・`.claude/rules/` を最新の状態に更新する（ファイルの追加・役割の変更・問題の解決／発見）。
- → この締めの手順は **`finish-task` スキル**にまとめてある。作業を終えるときは必ず使う。

## 進め方の方針（リードエンジニアとして）

言われたコードを書くだけでなく、プロジェクトの今の状態を見て、作業を速く・確実にする道具や進め方を自分から判断する。着手する前に次の3つを確かめる。

1. **Unity との連携**：エディタの操作は、まず今ある Unity CLI（`com.unity.pipeline`）で行う。CLI でできないことが出てきたときだけ、理由をつけて別の連携の導入を提案し、**許可をもらってから**入れる。（参考：Unity 公式の MCP サーバーは `com.unity.ai.assistant` に同梱済み〔`Modules/Unity.AI.MCP.Editor`〕。2026-11-12 の判断では CLI で足りるので使っていない）
2. **繰り返しの作業をスキルにする**：同じ手順を何度も行っていると気づいたら `.claude/skills/` にスキルとして置く。作る前に「何をスキルにするか」を一言伝える。
3. **ルールを分ける**：ある機能を触るときにしか要らない細かいルールは `.claude/rules/<機能>.md`（`paths:` で自動読み込み）に置き、ここには案内だけ残す。

- **自分で確かめてから渡す**：コードを書いたら、人に確認を頼む前に `unity-check`（再コンパイル・コンソール）と、必要なら `unity-playtest`（再生）で確かめる。エラーが出たらログを読んで直し、もう一度確かめる。直すのは今回自分が書いた部分だけ。
- **大きな設計は先に合意する**：仕組みの設計・複数の機能にまたがる変更・原因のわかりにくい不具合は、実装の前に「要件」と「方針」を書いて見せ、合意してから進める。
