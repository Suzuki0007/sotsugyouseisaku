対象期間：2026-11-07〜11-08（アイテム画面の作成 〜 タイトル画面・セーブスロット・メニュー画面まで）
目的：この期間に増えた仕組みを、これから一緒に作業するプログラマーが短時間で把握できるようにする。

- 既知の問題は「8. 既知の問題（すべて）」に全部載せています。ファイル単位の一覧は [`code-map.md`](code-map.md)、プランナー向けの手順は `Docs/` の各手順書にあります。

## 1. 全体像（変更の前と後）

| | アイテム画面を作る前 | 現在 |
|---|---|---|
| スクリプト数 | 約75 | 約170（うちエディタ拡張が多数） |
| 開始シーン | 各ステージから直接 | **`Title`** → `Stage1_1` ⇄ `Stage1_2`、`SceneGameOver`（Build Settings はこの4つ） |

| イベント | `EventZone` → `EventSequence`（全アクション同時実行） | **順番に実行（既定）**・待機・プレイヤー停止・セーブ復元、アイテム／フラグ条件で分岐 |

| 演出 | `SeManager`、`BgmManager` | ＋ `EffectManager`（エフェクト）、`SpriteAnimator`（連番アニメ） |
| UI | ライフ、タイミングゲージ、会話 | ＋ メニュー（Tab）、アイテム画面、タイトル、セーブスロット選択、確認ダイアログ、UI 効果音 |
| 入力停止 | 会話中だけ（各所に個別の if） | `InputBlock.IsBlocked` に一本化 |
| プランナー用ツール | ほぼなし | ひな形メニュー、シーンチェック、デバッグウィンドウ、会話 CSV、選択式の欄 |

方針は一貫して **「プランナーがコードを書かずに Inspector だけで作れる」** です。
プログラマーの仕事は「部品（EventAction・条件・コンポーネント）を増やすこと」と「土台（セーブ・入力・UI）を保つこと」が中心になります。

### 1-1. 設計の方針（なぜこうしているか）

| 方針 | 理由 | こうしなかった案と、その問題 |
|---|---|---|
| **データは ScriptableObject にする**（ItemData・GameFlag・SeData・EffectData・SpriteAnimData・DialogueData） | プランナーがアセットを**ドラッグするだけ**で指定でき、打ち間違いが起きない。参照は GUID なので、ファイル名を変えても切れない。1か所直せば全部の使用箇所に反映される | 文字列 ID や enum で指定する → 打ち間違いが実行するまで分からない。enum は増やすたびにコードの変更が要る |
| **ふるまいは小さな部品の組み合わせにする**（EventAction・条件・Trigger 系のコンポーネント） | 新しい演出が必要になっても**部品を1つ足すだけ**で、既存のコードを触らない。プランナーは Inspector で並べ替えて試せる | 1つの大きなイベントクラスに分岐を足していく → クラスが肥大化し、1つの変更が他のイベントを壊す |
| **既存の仕組みに乗せる・互換を保つ**（EventZone / EventSequence を流用、空の欄は従来どおり、KeyItem・Treasure は残す） | チームメンバーがすでに作ったシーンやプレハブを**壊さない**。シーンファイルの大きな書き換えは、git でのマージ衝突のもとになる | 古い仕組みを一気に置き換える → 全シーンの手直しが必要になり、作業中の人とぶつかる |
| **共通の判定や処理は1か所にまとめる**（InputBlock・UISound・MenuUIBuilder・SceneChecker） | 条件や見た目を変えるとき、**直す場所が1つ**で済む。直し忘れによる不具合が起きない | 各スクリプトで同じ判定を書く → 新しい画面を足すたびに5か所直す必要があり、実際に直し忘れの不具合が出た |
| **シーンに置き忘れても動く**（マネージャーと UI の自動生成） | 置き忘れで動かない、というミスをなくす。新しいシーンを作るときの手順も減る | シーンごとに置く → 実際に Stage1 / Stage2 では InventoryManager がなく、鍵を調べるとエラーになっていた |
| **ミスは実行前に見つける**（日本語の Tooltip、選択式の欄、シーンチェック、警告表示） | プランナーが一人で作業でき、プログラマーへの質問や「動かない」の調査が減る | 実行して初めて気づく → 原因を探すのにプログラマーの時間がかかる |

## 3. 守ってほしい約束（壊しやすいところ）

### 3-1. エディタのドメインリロードは無効 → static は自分でリセットする
Project Settings > Editor の Enter Play Mode Options で、ドメインリロードを無効にしています（再生開始を速くするため）。
そのため、**static 変数は再生を止めても残ります**。static を持つクラスには、必ず次を入れてください。

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void ResetOnPlay()
{
    // static の中身を空にする
}
```

- イベントの登録（`SceneManager.sceneLoaded += ...` など）は、**登録する前に一度 `-=` で外す**（再生のたびに二重登録されるため）。`AutoSave` がその例です。
- 実際にリセットしているクラス：`Save`、`GameFlags`、`GameSession`、`EventSequence`（ロック数）、`Health`（PlayerInvincible）、`PlayerSpawnPoint`（Pending*）、`SceneChange`（LastStageScene）、`ItemData`（キャッシュ）、`SeManager` など。

**理由**：ドメインリロードを有効に戻すと、再生を始めるたびに数秒待つことになり、試行錯誤の回数が減る（プロジェクト全員の設定にも関わる）。そこで「速さを取り、static は各クラスが責任を持ってリセットする」ことにした。`SubsystemRegistration` は、どの初期化よりも先に呼ばれるので、ほかのクラスの初期化がリセット前の値を読む心配がない。実際に「再生を止めても前回の所持品・セーブが残る」「AutoSave の処理が再生のたびに増える」という不具合があり、この形で直した。

### 3-2. 自動で生成されるもの（シーンに置かなくてよい）
| もの | 生成のされ方 | シーンをまたぐか |
|---|---|---|
| `InventoryManager` | 最初のシーンになければ AfterSceneLoad で生成 | ○ |
| `GameMenu` | `Resources/UI/GameMenu.prefab` から生成 | ○ |
| `ItemMenuUI` | `Resources/UI/ItemMenu.prefab` から生成 | ○ |
| `SceneFader` | 初めて使ったときに生成 | ○ |
| `EffectManager` | 初めて使ったときに生成 | ○ |
| `UISubmitKeys` | 起動時に生成 | ○ |
| `DialogueManager` | **自動生成しない**。シーンに `Assets/Prefab/UI/DialogueSystem.prefab` を置く | ×（シーンごと） |

- 自動生成する UI のプレハブは **エディタ拡張（Builder）で作っています**（`Tools > メニュー画面`、`Tools > アイテム画面`、`Tools > タイトル画面`）。**Builder で作り直すと、手で調整した見た目は上書きされます。** 見た目をプレハブで直したら、Builder 側にも反映するか、作り直さないようにしてください。

**理由**：
- **自動生成**：メニュー・アイテム画面・暗転などはどのシーンでも同じものが要る。シーンごとに置く方式だと、置き忘れたシーンで動かない（実際に InventoryManager で起きた）。`DontDestroyOnLoad` で1つを使い回すので、所持品やメニューの状態もシーンをまたいで保てる。
- **Resources から生成**：プレハブにしておけば見た目は Inspector で調整できる。コードの中で UI を組み立てる方式と違い、デザインの変更にコードの修正が要らない。
- **Builder でプレハブを作る**：UI の階層を手で組むと手順が多く、人によって作りが変わる。コードで作れば何度でも同じものを作り直せ、壊れたときの復旧も一瞬で済む。`MenuUIBuilder` を共通にしたのは、タイトル・メニュー・セーブ画面のボタンや配色を揃えるため。
- **DialogueManager だけシーンに置く**：会話 UI はシーン側の Canvas と組み合わせて使ってきた経緯があり（Stage1_2 はシーンの Canvas に直接組んである）、今はシーンごとに置く形を残している。揃えるなら DialogueSystem.prefab に統一する。

### 3-3. プレイヤーの入力を止める判定は `InputBlock.IsBlocked` だけ
```csharp
public static bool IsBlocked =>
    DialogueManager.IsBusy || SceneFader.IsBusy || ItemMenuUI.IsBusy ||
    EventSequence.IsBusy || GameMenu.IsBusy;
```
- 新しく「操作を止めたい画面・演出」を作ったら、**ここに条件を足すだけ**にしてください。各所に個別の if を書かないでください。
- 見ている側：`PlayerInput`、`AttackController`、`PlayerSwitchManager`、`Intaractable`、`TimingGaugeUI`。
- 各 `IsBusy` は「開いている、または**開閉した直後のフレーム**」も true です。同じキーで閉じて別のものが開く、という事故を防ぐためです。新しい画面を作るときも同じ形にしてください。

**理由**：以前は各スクリプトに `DialogueManager.IsBusy || SceneFader.IsBusy || ...` を書いていたため、画面を1つ足すたびに5か所を直す必要があった。直し忘れると「メニューを開いている間に Space で攻撃が出る」のような不具合になる。1か所にまとめれば、新しい画面は1行足すだけで全部の入力が止まる。
「開閉した直後のフレーム」も含めるのは、Unity では同じフレームのどのスクリプトの Update が先に動くかが決まっていないため。たとえば E キーで会話を閉じたフレームに、調べる処理が同じ E を拾うと、会話がすぐ開き直してしまう。

### 3-4. セーブは「仮置き → 確定 → 書き込み」
```
Save.SetPending(key, value)   … 仮置き（まだ確定していない）
        │
Save.Commit()                 … 確定（BeforeCommit でプレイ時間・保存日時・再開場所も記録）
        │
Save.Write() / WriteAsync()   … 使っているスロットのファイルへ（スロット未使用なら書かない）
```
- **確定するタイミング**：シーンに着いたとき（`PlayerPartySpawner.Start`）、シーンを出るとき（`SceneChange`）、`CheckPoint`、セーブポイント、終了時。
- 進行に関わる状態（拾った・開けた・完了した・フラグ）は **`SetPending` で記録**してください（`Set` で直接確定させない）。
- `Save.Get` は仮置きを優先して読みます。
- 新しいキーは、下の名前の規則に合わせてください。

| キー | 中身 | 書く側 |
|---|---|---|
| `Inventory/Items` | `ID:個数` のカンマ区切り（取得順） | `InventoryManager` |
| `Flag/<id>` | フラグの ON/OFF（セーブするフラグだけ） | `GameFlags` |
| `Pickup/<scene>/<id か階層パス>` | 拾ったか | `ItemPickup`、`KeyItem` |
| `Interaction/<scene>/<id か階層パス>` | 完了したルールの番号 | `ItemInteraction` |
| `<scene>/<宝箱id>` | 開けたか | `Treasure`（古い形式） |
| `Meta/*` | 再開するシーン・出現位置・座標・プレイ時間・保存日時 | `GameSession`、`SaveSlotInfo` |

- ID が空のとき「階層パス」を使う部品は、**オブジェクトの名前や親を変えると記録がリセットされます**。プランナーには ID を入れてもらうよう伝えてください（シーンチェックで重複を検出できます）。

**理由**：
- **仮置きと確定を分ける**：「最後にセーブした時点に戻る」というゲームの仕様に合わせるため。拾った・開けたをすぐファイルに書くと、セーブせずにタイトルに戻っても進行が残ってしまう。確定のタイミングを決めておけば、途中の中途半端な状態がファイルに残ることもない。
- **書き込みは WriteAsync**：シーン切り替えのたびにファイル書き込みで画面が止まらないように、別スレッドで書く。
- **キーと値（文字列）で持つ**：仕組みが単純で、新しい保存項目を足すときにデータの形（クラス）を変えなくてよい。古いセーブを読んでも、知らないキーは無視されるだけで壊れない。
- **ID が空なら階層パス**：プランナーが ID を入れ忘れても一応動くようにするため。ただし名前の変更に弱いので、ID を入れる運用を勧めている。
- **スロットを使っていなければ書かない**（`CurrentSlot = 0`）：エディタでステージから直接再生して試すたびに、ユーザーのセーブが書き換わらないようにするため。

### 3-5. イベントの部品は `EventAction` を継承する
```csharp
public abstract void Execute(GameObject gameObject);            // 実行
public virtual IEnumerator Run(GameObject gameObject)           // 終わるまで次を待たせたいとき（既定は Execute して即終了）
public virtual void OnExit(GameObject gameObject) { }           // エリアから出たとき
public virtual void Restore(GameObject gameObject) { }          // セーブから復元するとき（見た目だけ。会話・SE は出さない）
```
- `EventSequence` は **既定で順番に実行**します（`Run` が終わるのを待つ）。
- `Restore` は「完了済みのイベントを、シーンを読み込み直したときに完了後の見た目にする」ためのものです。**表示切り替え・スプライト・アニメの最終コマなど「状態」を変える部品だけ**がオーバーライドします。

**理由**：
- **Execute と Run を分ける**：ほとんどの部品は一瞬で終わるので Execute だけ書けばよい。待つ必要がある部品（会話・待機・アニメ）だけが Run をオーバーライドする。全部の部品にコルーチンを書かせるより、部品を作る手間が少ない。
- **既定を「順番に実行」にした**：「会話が終わってから扉が消える」「一拍おいて会話」といった演出は、順番がないと作れなかった。全部同時に実行したいことのほうが少ない。
- **Restore を Execute と別にした**：シーンに戻ったとき、Execute をもう一度呼ぶと会話や SE まで再生されてしまう。部品ごとに「完了後の見た目」を知っているのは部品自身なので、各部品に任せた。代わりに「すべてのオブジェクトの表示状態をセーブする」方式も考えられるが、保存するものが多く、シーンを編集したときに壊れやすい。

### 3-6. プランナー向けのコードの書き方
- Inspector に出る項目には **日本語の `Tooltip`**、enum には `InspectorName` を付けてください。
- 項目名を日本語にするときは **`[Label("日本語")]`**（`InspectorName` は enum の値にしか効かず、項目に付けても英語のままになる）。最小値・スライダーは `[Label("名前", min)]` / `[Label("名前", min, max)]` で指定し、`Range` / `Min` とは一緒に付けない（属性の表示は1つしか効かないため）。リストに付けると要素ごとの名前が変わるので、リストは `Tooltip` で説明する。
- 新しい機能には `Docs/` に手順書を書いてください（または既存のものに追記）。
- ひな形が作れるもの（Hierarchy 右クリック、`Tools` メニュー）は、`Editor/` フォルダに Creator / Builder を置いています。
- ファイルの先頭のヘッダーコメント（`\file` `\brief` `\author`）、`//===` の区切り、`if(x) { ... }` の1行スタイル、日本語のコメントに合わせてください。
- `ItemData` は **`Assets/Resources/Items/` 以下に置く必要があります**（セーブから復元するとき、`Resources.LoadAll` で ID から探すため）。

**理由**：このプロジェクトの目標は「プランナーがコードを書かずに作れる」こと。Tooltip や手順書があれば、プランナーがプログラマーに聞かずに進められ、プログラマーは部品作りに時間を使える。
`Resources/Items` に置くのは、セーブには ID（文字列）しか残らないため、読み込むときに「ID → ItemData」を探す手段が必要だから。全アイテムを並べた一覧アセットを作る方式だと、アイテムを足すたびに一覧への登録が必要になり、登録忘れが起きる。フォルダに置くだけの方式のほうがミスが少ない（フォルダの外に置いたものはシーンチェックで見つかる）。

## 4. 仕組み別の解説

### 4-1. アイテム（`Item/`、`Manager/InventoryManager.cs`、`UI/ItemMenu/`）
- **`ItemData`**：ID・表示名・説明・アイコン・`Is Key`。`ItemData.Find(id)` で ID から探します（`Resources/Items` が対象）。
- **`InventoryManager`**（`Singleton`、シーンをまたぐ）
  - `AddItem(item, n)` / `RemoveItem(item, n)` / `GetCount(item)` / `HasItem(item)` / `ConsumeKey()`
  - `OnChanged` イベントで、UI や ItemPossessionSwitch に変化を知らせます。
  - `ReloadFromSave()`：スロットを切り替えたときに、所持品をセーブから読み直します（GameSession が呼びます）。
  - `NoahData.hasKey` は古い仕組みとの互換用です。`Is Key` のアイテムの増減に合わせて更新しています。
- **`ItemPickup`**（Intaractable）：調べると入手し、`Pickup/...` に記録します。拾ったものは復活しません。
- **`ItemMenuUI`**：一覧と詳細（名前・説明・アイコン・個数）。開いている間は `Time.timeScale = 0` です。プレハブは `UI/ItemMenu/Editor/ItemMenuCreator.cs` で作ります。
- 古い **`KeyItem` / `Treasure`** はシーンで使われているので残しています。ItemData を使う形に寄せてあり、鍵は個数で持て、宝箱を開けると1本消費します（`Consume Key`）。ItemInteraction への置き換えは ⑦ として未着手です。

**なぜこの形か**：
- **所持品は「種類の一覧（取得順）＋個数」**：アイテム画面で取得順に並べたい、同じ鍵を複数持ちたい、の両方を満たすため。最初は「1種類1個」だったが、「鍵を持っていると別のステージの鍵が拾えない」問題があり、個数制にした。
- **拾ったかどうかは、アイテムではなく置いたオブジェクトごとに記録**（`Pickup/...`）：アイテムを消費して0個になっても、拾った場所に復活しないようにするため。「持っているか」で表示を決めると、使ったあとにシーンに戻ると何度でも拾えてしまう。
- **`OnChanged` イベントで知らせる**：アイテム画面や ItemPossessionSwitch が毎フレーム所持品を調べなくてよい。変わったときだけ更新するので、無駄な処理がない。
- **メニューを開いている間は `Time.timeScale = 0`**：メニューを見ている間に敵の弾が当たらないようにするため。UI 側は時間停止の影響を受けない処理（unscaled）で動かしている。
- **古い API（`NoahInventory.GetKey` / `HasKey`、`NoahData.hasKey`）を残した**：宝箱や鍵など、それを使っている既存のコードとシーンをそのまま動かすため。

### 4-2. アイテム連動イベント（`Item/Interaction/`）
考え方は「**きっかけ × 条件 × 結果**」です。
```
ItemInteraction（Intaractable を継承）
  Trigger : 調べたとき / エリアに入ったとき
  Rules   : 上から順に調べ、最初に条件を満たしたものだけ実行
      conditions      : List<ItemCondition>（アイテム・個数・持っていないとき）
      flagConditions  : List<FlagCondition>（ON / OFF）       … アイテム条件と AND
      consumeItems    : 条件のアイテムを消費する
      sequence        : 実行する EventSequence
      markCompleted   : 実行したら完了（Interaction/... に保存）
  Otherwise       : どのルールも満たさないとき
  After Completed : 完了後に調べたとき
```
- 完了済みなら、`Start` で `sequence.Restore()` を呼んで見た目だけを戻します。
- **`ItemPossessionSwitch`**：所持状況で表示を切り替え続けます（`OnChanged` を購読）。フラグ版は `FlagSwitch` です。
- `Intaractable` に `OnPlayerEnter` / `OnPlayerExit`（virtual）を足しています。「エリアに入ったとき」のきっかけはこれを使っています。
- 手順書：`Docs/アイテム連動イベントの作り方.md`、サンプル：`Tools > アイテム連動 > サンプルを配置`。

**なぜこの形か**：
- **「上から順に調べて、最初に満たしたルールだけ」**：プランナーが考える「もし〜なら／そうでなく〜なら／それ以外」をそのまま表せる。ルールの中は AND、「A か B」はルールを2つ並べる、と決めておけば、条件式を組み立てる画面を作らずに済み、読み間違いも起きにくい。
- **結果は既存の `EventSequence` に任せる**：会話・SE・BGM などの部品をそのまま使え、プランナーの作業の流れも変わらない。ItemInteraction 自身は「どれを実行するか決める」ことだけに集中できる。
- **条件は `[Serializable]` のクラスのリスト**（`ItemCondition` / `FlagCondition`）：Inspector の中にそのまま並び、条件のためにオブジェクトを増やさなくてよい。BGM の条件（`BgmCondition`）はコンポーネント式で、条件ごとにオブジェクトが要る。新しく作る条件はリスト式に揃える。
- **完了をルールの番号で保存**：どのルールで完了したかが分かれば、復元のときにそのルールの `Restore` だけを呼べる。
- **`Intaractable` には仮想関数を足しただけ**：既存の宝箱・鍵・会話など、Intaractable を継承するクラスの動きを変えないため。

### 4-3. イベントの実行（`Event/`）
- **`EventSequence`**
  - `Play Mode`：順番に実行（既定）／すべて同時に実行
  - `Lock Player`：実行中は `EventSequence.IsBusy` が true になり、プレイヤーの入力が止まります（ロック数で管理）。
  - Actions が空なら、同じオブジェクトの EventAction を上から順に使います。
  - 実行中に再生を頼まれても無視します。`Stop()` で中断できます。
- 部品：`DialogueEventAction`（Wait Until Closed）、`SeEventAction`、`SetActiveEventAction`、`SpriteChangeEventAction`、`AnimEventAction`（Wait Until Finished）、`EffectEventAction`、`WaitEventAction`、`ItemGiveEventAction`、`ItemTakeEventAction`、`SetFlagEventAction`、BGM 系。
- **注意**：順番に実行している途中で、自分（か親）のオブジェクトを非表示にすると、コルーチンが止まって後ろの部品が動きません。シーンチェックで検出できます。
- **既存のイベントへの影響**：#5 で既定が「順番に実行」になったため、会話の後ろに並べた部品は**会話を閉じてから**動くようになりました。
- 手順書：`Docs/イベントの順番と待ち時間.md`。

**なぜこの形か**：
- **コルーチンで順番に実行**：「待つ」を自然に書けて、部品を作る側は `yield return` で終わりを示すだけでよい。状態遷移を自前で管理する方式より、部品のコードが短い。
- **Lock Player はロック数で管理**：複数のイベントが同時に止めることがあっても、全部が終わるまで入力が戻らないようにするため（bool だと、先に終わったイベントがロックを外してしまう）。
- **Actions が空なら同じオブジェクトの部品を上から使う**：リストへの登録を忘れても動くようにするため。登録漏れは Inspector の警告とシーンチェックでも知らせる。
- **実行中の再生要求は無視**：同じイベントが二重に動いて、会話が重なったりアイテムを2回もらえたりするのを防ぐため。

### 4-4. フラグ（`Flag/`）
- **`GameFlag`**（ScriptableObject）：ID・メモ・セーブするか。
- **`GameFlags`**（static）：セーブするフラグは `Save` の `Flag/<id>` へ（SetPending）、しないフラグはメモリに持ちます（一時フラグ）。`OnChanged` で変化を知らせます。
- `BgmFlags` は GameFlags の一時フラグに統合しました。API は互換です（同じ ID なら同じフラグ）。
- エディタ：`Tools > フラグ > フラグ一覧`（再生中に切り替え可）、Hierarchy 右クリック > フラグ。
- 手順書：`Docs/フラグの使い方.md`。

**なぜこの形か**：
- **フラグもアセットにした**：文字列のフラグ名だと、設定する側と判定する側で1文字違うだけで動かない。アセットをドラッグする方式なら打ち間違いが起きず、「このフラグはどこで使っているか」も追える。
- **「セーブする／しない」をフラグごとに選べる**：進行（ボスを倒した）は残し、一時的な状態（ボス部屋の中にいる）は残さない、を1つの仕組みで扱うため。
- **BgmFlags を統合した**：BGM 用とイベント用でフラグが別々だと、同じことを2回設定する必要があった。API は変えていないので、既存の BGM の設定はそのまま動く。

### 4-5. エフェクト（`Effect/`）
- **`EffectData`**（連番スプライトか Prefab、消え方、位置・大きさ・向き、表示順、同時に鳴らす SE、連打対策）
- **`EffectManager.Play(data, position / follow)`** → `EffectHandle`。プールで使い回します。`Stop` / `StopAll`。
- **`EffectTrigger`**：コードなしで「いつ（出現・消滅・被ダメージ・回復・死亡・接触・手動）・どれを・どこに」出すかを設定できます。
- 弾・敵・攻撃のクラスにエフェクト欄があります。**空なら従来どおり**の動作です。
- 手順書：`Assets/Script/Effect/README_エフェクトの使い方.md`。

**なぜこの形か**：
- **プールで使い回す**：弾の命中のように短い間に何十回も出るものを、毎回 Instantiate / Destroy すると処理落ちやメモリの掃除（GC）の原因になる。
- **出すタイミングを EffectTrigger に分けた**：「いつ出すか」をコードに書くと、出したい場面が増えるたびにプログラマーの作業になる。よく使うタイミングを部品にしておけば、プランナーが自分で付けられる。
- **欄が空なら従来どおり**：エフェクトの素材がまだない段階でも、既存の弾や敵がそのまま動くようにするため。

### 4-6. スプライトアニメーション（`SpriteAnimation/`）
- **`SpriteAnimData`**（動きごとの画像・速さ・再生のしかた・コマのイベント。上下左右／左右／向きなしに対応）を、**`SpriteAnimator`** が再生します（Animator は使いません）。
- **`CharacterAnimLink`**：実際の移動量から Idle / Walk と向きを自動で切り替え、Health のダメージで Damage を流します。
- `NoahDead` / `EnemyDead` は「Dead」の動きがあれば、流し終わってから消える・ゲームオーバーへ移ります。
- 古い `NoahAnimation` / `SigleAnimation` / `SpriteAnimation`（Animator 版）は、SpriteAnimator があれば何もしません。
- 手順書：`Assets/Script/SpriteAnimation/README_アニメーションの使い方.md`。

**なぜこの形か**：
- **Animator を使わず自前で再生**：2D の連番アニメに必要なのは「画像を順に出す・向きを変える・終わったら次へ」くらいで、Animator Controller の状態遷移を組むのはプランナーには難しい。画像を選んで右クリックで作れるデータ形式のほうが、素材の差し替えも速い。
- **画像の名前から動きと向きを自動で振り分ける**：数十枚の画像を1枚ずつ欄に入れる手間をなくすため。
- **CharacterAnimLink は「実際に動いたか」で判断する**：操作キャラ・付いてくる仲間・敵のどれにも、入力の仕組みに関係なく同じ部品を付けられるようにするため。
- **コマの計算をエフェクトと共通化**（`SpriteFrameTiming`）：同じ計算が2か所にあると、片方だけ直して食い違うのを防ぐため。

### 4-7. タイトル・セーブスロット（`Title/`、`Save/`）
```
Title（TitleMenu）
  はじめから → スロット選択（使用中なら上書き確認）→ GameSession.StartNewGame(slot, 最初のシーン, 出現位置)
  つづきから → スロット選択 → GameSession.Continue(slot, …)
                   └ Save.LoadSlot → Meta/* から PlayerSpawnPoint.PendingSpawnPointId / PendingPosition を設定
  → InventoryManager.ReloadFromSave → SceneFader でステージへ

ステージ（PlayerPartySpawner.Start）
  ConsumePendingPosition → ConsumePending（出現位置ID）→ 既定の位置 の順で出現位置を決める
  着いた場所を「再開する場所」として記録 → Save.Commit + WriteAsync
```
- **`Save`**：`CurrentSlot`（0 = スロットを使わない → ファイルに書かない）、`LoadSlot` / `StartNewSlot` / `SaveToSlot` / `CloseSlot` / `PeekSlot` / `DeleteSlot`。旧 `save.json` は起動時にスロット1へ移します（`MigrateLegacy`）。
- **`GameSession`**（static）：はじめから・つづきから・タイトルへ・`SaveAt`、プレイ時間（`PlayTimeCounter`）。
- **`SaveSlotInfo`**：`Meta/*` キーの定義と、スロットの概要（場所・プレイ時間・保存日時）の読み込み。
- **`AutoSave`**：エディタでステージから直接再生したときだけ、デバッグウィンドウで選んだスロットを読みます。
- 手順書：`Docs/タイトル画面とセーブの仕組み.md`。

**なぜこの形か**：
- **再開場所は「出現位置 ID」か「座標」**：扉で移動したときは出現位置 ID で再開すれば、マップを手直しして座標がずれても再開場所が壊れない。セーブポイントやチェックポイントは任意の場所なので座標で持つ。
- **シーンに着いたときに自動で確定する**：「つづきから」が必ず最後にいたシーンの入口から始まるようにするため。セーブポイントまで戻らないと進行が失われる、という厳しさを避けた。
- **`GameSession` に「はじめから・つづきから・タイトルへ」をまとめた**：タイトル・メニュー・ゲームオーバー画面がそれぞれセーブの手順を持つと、所持品の読み直しや一時フラグの消し忘れが起きる。手順を1か所にまとめて、どこから呼んでも同じ状態になるようにした。
- **エディタでの直接再生は、初期値でセーブを読まない・書かない**：作業中に何度も再生しても、テストプレイ用のセーブデータが勝手に書き換わらないようにするため。

### 4-8. メニュー・セーブポイント・共通 UI（`UI/GameMenu/`、`SavePoint/`、`UI/Common/`）
- **`GameMenu`**：Tab で開閉（ゲーム停止）。アイテム（閉じるとメニューに戻る）／ロード／タイトルに戻る。`OpenSave(...)` でセーブの流れ（確認 → スロット選択 → `GameSession.SaveAt` → メッセージ）。プレイヤーがいるシーンでだけ開きます。
- **`SavePoint`**（Intaractable）：調べると `GameMenu.OpenSave`。`Resume Offset` の位置から再開します。
- **共通部品**：`SaveSlotPanel`（NewGame / Continue / Load / Save の4用途）、`ConfirmDialog`（はい／いいえ、Esc = いいえ、初期選択はいいえ）、`PlaceNameTable`（場所の表示名）、🛠`MenuUIBuilder`（ボタン・スロット画面・ダイアログを作る共通処理）。
- **UI の効果音**：`UISound.Play(UISoundType.Decide)` など。音は `Resources/UISounds.asset` で一括管理しています。ボタンには `UIButtonSound` を付けます。
- **決定キー**：`UISubmitKeys` が、実行中だけ EventSystem の Submit に Space を足します（パッケージの DefaultInputActions は書き換えていません）。

**なぜこの形か**：
- **SaveSlotPanel を4用途で共通にした**：はじめから・つづきから・ロード・セーブは「スロットを選ぶ」部分が同じ。画面を4つ作ると、見た目や操作が少しずつ食い違う。
- **UI の効果音を1つのアセットで管理**：画面ごとに音を設定すると、音を差し替えるときに全部の画面を回る必要がある。各画面の個別の欄は「空なら共通の音」にして、特別な音にしたいときだけ使う。
- **Space をパッケージを書き換えずに足した**：Input System のパッケージの中身を書き換えると、パッケージを更新したときに消える。実行中に足す方式なら、更新に影響されない。
- **確認ダイアログの初期選択は「いいえ」**：上書きやタイトルに戻るなど、取り消せない操作をキーの連打で決定してしまわないようにするため。

### 4-9. プランナー用ツール（`Common/`、各 `Editor/`）
| ツール | 場所 | プログラマーが関わるところ |
|---|---|---|
| 選択式の欄 | `[SceneName]`、`[SpawnPointId(nameof(field))]` 属性 | シーン名・出現位置 ID の string に付けるだけでドロップダウンになる |
| シーンチェック | `Tools > シーンチェック` | 設定ミスの検査を増やすときは `SceneChecker.CheckScene` / `CheckProject` に足す |
| デバッグウィンドウ | `Tools > デバッグ` | アイテム・フラグ・ワープ・回復・無敵・セーブ操作。`PlayerSwitchManager.Warp`、`Health.PlayerInvincible` |
| 会話 CSV | `Tools > 会話`、CSV を右クリック | `DialogueCsv.Import(path, showDialog:false)` でスクリプトからも呼べる |

- 手順書：`Docs/プランナー用ツールの使い方.md`。

**なぜこの形か**：
- **シーン名・出現位置 ID を選択式にした**：遷移先の打ち間違いは、実際にその扉を通るまで気づけない。選択式にすれば、そもそも間違えられない。閉じているシーンの ID はシーンファイルから読むので、行き先のシーンを開かなくてよい。
- **シーンチェック**：ID の重複・トリガーの付け忘れ・自分を非表示にして止まるイベントなどは、遊んでも気づきにくい。まとめて一覧にすれば、作業の最後に一度見るだけで済む。
- **デバッグウィンドウ**：後半のイベントを確かめるたびに最初から遊ぶのは時間がかかる。アイテムやフラグを与えて途中から始められるようにした。設定を EditorPrefs に置いたのは、個人のテスト用の設定がほかの人やビルドに影響しないようにするため。
- **会話 CSV**：台本は Excel やスプレッドシートで書くほうが速く、チームでも共有しやすい。同じ会話 ID なら上書き（GUID を保つ）にしたのは、取り込み直してもシーンの参照が切れないようにするため。

### 4-10. 敵（`Enemy/`、`Damage/`、`Enemy/Navigation/`）※段階ごとに作っている途中
今あるのは段階1（土台）まで。行動パターン・攻撃・部位・追跡などは段階2以降で足す。手順書は `Docs/敵の作り方.md`。

| 部品 | 役割 |
|---|---|
| `EnemyData`（ScriptableObject） | 敵1種類の設定（体力・速さ・大きさ・体当たり・見た目・倒されたとき） |
| `Enemy`（共通プレハブ `Prefab/Enemies/Enemy_Base`） | データの反映、Rigidbody2D での移動、`MoveTo` で経路に沿って進む、マップの範囲内、体当たり、倒されたときの演出、`Paused`、`Enemy.All` |
| `DamageInfo` / `DamageKind` / `PlayerCharacters` | 攻撃の情報（量・種類・攻撃者・キャラ・位置・ゲージ判定） |
| `DamageReceiver` / `DamageUtility` | 攻撃を受ける部品（部位・ギミック用）と、攻撃を当てる共通の入口 |
| `EnemyBlock` | 敵を止める判定（`InputBlock` + デバッグ） |
| `NavMesh2D` / `EnemyNavArea` | 2D の経路探索／敵だけ入れない・通りにくい場所 |
| `GameCondition`（`Common/`） | 条件のまとめ（フラグ・アイテム・操作キャラ・体力・範囲） |

**守ってほしいこと**：
- 攻撃を当てる処理を新しく書くときは、`GetComponent<Health>().Damage()` ではなく **`DamageUtility.Apply(collider, DamageInfo)`** を通す。
- 敵の動き・攻撃を止める条件は **`EnemyBlock.IsBlocked`** だけを見る（増やすときはここに足す）。
- 敵は transform を直接動かさない（`Enemy` が Rigidbody2D の速度で動かす。外からは `MoveTo` / `Stop` / `Paused`）。

**なぜこの形か**：
- **敵を「データ＋共通プレハブ」にした**：アイテム（ItemData）と同じ作り方にそろえ、敵を増やすときはデータを複製するだけにするため。プレハブを敵ごとに作ると、部品の付け忘れや設定のばらつきが起きる。
- **`Damage(int)` を残して `Damage(DamageInfo)` を足した**：Health を使う所が8か所（ライフ・SE・エフェクト・アニメ・BGM・死亡など）あり、呼び出し方を変えると全部が壊れる。足す形なら今のコードはそのまま動き、「誰の・どの攻撃か」を見たい所だけが新しい方を使える。
- **攻撃を当てる入口を `DamageUtility.Apply` に集めた**：今までは範囲攻撃・弾がそれぞれ `GetComponent<Health>()` を呼んでいて、部位（子オブジェクト）に当てる方法がなかった。入口が1つなら、部位・弱点・ギミックの反応を1か所で足せる。範囲攻撃の「同じ相手に1回だけ」を Health 単位にしたのも、本体と部位に同時に当たって2倍のダメージになるのを防ぐため。
- **敵を Rigidbody2D（Dynamic）で動かす**：Static のまま transform を動かすと壁をすり抜ける（古い敵の問題）。Kinematic は壁で止まらない。Dynamic にして回転を止め、「押されにくい」敵は重くしている。
- **経路探索は Unity 標準の NavMesh に 2D 用の部分を自作した**：NavMesh は 3D 用で、2D のコライダーや Tilemap を集められない。外部の拡張（NavMeshPlus）は Unity の更新で壊れたときに直せないので使わず、経路の計算（いちばん難しい所）だけ Unity に任せた。ナビメッシュを X 軸で -90° 回すと XY 平面に重なり、経路はそのままワールド座標で聞ける。
- **NavMeshAgent を使わない**：Agent は transform を自分で動かすので、Rigidbody2D の移動・壁・ノックバック・停止と二重になる。経路だけを計算し、動かすのは `Enemy` に任せた。
- **壁はコライダーの形のメッシュを床より手前に置く**：`Collider2D.CreateMesh` で四角・円・多角形・Tilemap の形をそのまま使える。床と同じ高さに置くと「歩ける床」と混ざって通れてしまうので、登れる高さより上・通れる高さより下に置き、真下の床を通れなくしている（このとき壁の周りが敵の半径ぶん自動で削られる）。
- **自動で作り、0.5 秒ごとに作り直す**：プランナーが「作り直し」のボタンを押し忘れると、扉を開けても敵が通れない。壁の状態の目印（位置・大きさ・有効か）を比べ、変わったときだけ裏で作り直す。作り直し中は材料（メッシュ・リスト）を変えない。
- **大きさごとに別のナビメッシュ**：通れる幅は敵の半径で決まる。1つのナビメッシュでは大きい敵が細い通路に入り込むので、小中大で分けた（使う大きさだけ作る）。
- **`GameCondition` は既存の条件を中に持つ**：`FlagCondition` / `ItemCondition` はシーンやデータで使われていて、作り替えると保存された設定が消える。外側から包むだけにした。

## 5. 既存のコードの動きが変わったところ（要注意）

以前の動作を前提にしたコードやシーンがあれば、確認してください。

| 変更 | 影響 | 変えた理由 |
|---|---|---|
| `EventSequence` の既定が「順番に実行」 | 会話の後ろの部品は会話を閉じてから動く。元に戻すなら Play Mode を「すべて同時に実行」 | 「会話のあとで扉が消える」などの演出が作れなかったため |

| 鍵が個数制に | 鍵を持っていても別の鍵を拾える。`Treasure` は既定で鍵を1本消費する | 鍵を持っていると別のステージの鍵が見えず、使ったあとに不自然な状態になったため |

| 弾が味方とトリガー範囲を通り抜ける | イベント範囲や調べる範囲に当たって消えなくなった | 見えない範囲に当たって弾が消えるのは、遊ぶ人から見て不自然なため |
| `BulletDeleteArea`、`BulletPoolBase`、`PlayerBulletPool` の修正 | 弾が増え続ける・消えない問題の解消 | 不具合（null 参照・上限を超えた弾が残る・プールに戻らない）の修正 |
| 開始シーンが `Title` に | エディタでステージから直接再生したときは、セーブを読まない（デバッグウィンドウで選べる） | セーブスロットを選んで始める流れが必要になったため |

| シグルの射撃（`PlayerInput.Update` で左クリックを直接読む、プレハブに `SigleShooter`、Target Camera が空ならメインカメラ） | シグル操作中に左クリックで撃てるようになった。`OnShot` は Input System のイベント用に残しているが、どこからも呼んでいない | 撃てない原因が3つ重なっていた。Input System の PlayerInput コンポーネントを足すより、移動・Q と同じく Update で読むほうが、入力の読み方が1か所にそろうため |
| 範囲攻撃・弾が `DamageUtility.Apply` を通すように | 当たった相手に `DamageReceiver` があればそちらに渡す（なければ今までどおり Health）。範囲攻撃の「同じ相手に1回だけ」は、GameObject ごとから **Health ごと**に変わった | 部位・ギミックに攻撃を当てられるようにするため。本体と部位の二重ヒットを防ぐため |
| `EnemyShooter` が狙う相手と弾のプールを自分で探す。`EnemyBlock` の間は撃たない | スポナーなしで置いた古い敵も撃つ。会話・イベント中は撃たない（移動は Behavior Graph なので続く） | 会話中に撃たれてやられるのを防ぐため。スポナーに頼らず置けるようにするため |
| `EnemySpawner` が BehaviorGraphAgent / EnemyShooter のない敵でもエラーにしない | 新しい作りの敵（Enemy）もスポナーから出せる | 新旧どちらの敵も同じスポナーで使えるようにするため |
| **2人で体力を共有**（`Health.ShareWith`。シグルのプレハブに Health、`PlayerPartySpawner` がシグル → ノアを設定） | 敵の攻撃がシグルに当たると、ノアの体力が減る（以前はダメージなしで弾が消えていた）。シグルの Health の `OnDamaged` も出るので、シグルのダメージのアニメ・エフェクトが動く。`BgmConditionHealth` はシグル操作中も効く | ライフ表示・ゲームオーバーはノアの体力だけを見ているので、それを変えずに「シグルも攻撃を受ける」ようにできる。共有先へ回す形なので、`Health` を使う8か所（ライフ・SE・エフェクト・アニメ・BGM・死亡など）はどれも変更不要 |

## 6. よくある作業のやり方

### 新しいイベントの部品を作る
```csharp
/*********************************************************************/
// * \file   ShakeCameraEventAction.cs
// * \brief  イベントでカメラを揺らすアクション
// *
// * \author
/*********************************************************************/

using System.Collections;
using UnityEngine;

/// <summary>
/// イベントでカメラを揺らすアクション（例）
/// </summary>
public class ShakeCameraEventAction : EventAction
{
    [SerializeField, Tooltip("揺らす時間（秒）")]
    private float duration = 0.5f;

    [SerializeField, Tooltip("揺れ終わるまで次の部品を待たせる")]
    private bool waitUntilFinished = true;

    public override void Execute(GameObject gameObject)
    {
        // 揺らし始める
    }

    public override IEnumerator Run(GameObject gameObject)
    {
        Execute(gameObject);
        if(waitUntilFinished) { yield return new WaitForSeconds(duration); }
    }

    // 状態が残る部品（表示・見た目）なら Restore もオーバーライドする
}
```
- 作ったら、`Docs/アイテム連動イベントの作り方.md` か `Docs/イベントの順番と待ち時間.md` の部品一覧に追記してください。
- `WaitForSeconds` は timeScale の影響を受けます（メニューを開いている間は止まる）。止めたくないなら `WaitForSecondsRealtime` を使います。

### 新しい条件を作る
- アイテム条件は `ItemCondition`、フラグ条件は `FlagCondition` で、どちらも `[Serializable]` のクラスに `IsMet()` と `AllMet(list)` を持たせています。新しい種類（例：所持金・体力）も同じ形で作り、`ItemInteraction.Rule` に List を足して AND で判定するのが一番簡単です。

### プレイヤーを止める新しい画面・演出を作る
1. `public static bool IsBusy`（開いている、または開閉した直後のフレーム）を用意する
2. `Common/InputBlock.cs` に足す
3. 開いている間ゲームを止めるなら、`Time.timeScale` を保存してから 0 にし、閉じたときと **OnDestroy で戻す**（シーン遷移で破棄されても止まったままにならないように）

### セーブする状態を足す
1. キーを `機能名/<scene>/<id>` の形で決める（3-4 の表に追記）
2. 変わったときに `Save.SetPending(key, value)`、読み込みは `Save.Get(key, 既定値)`
3. スロットを切り替えたときに読み直す必要があるなら、`GameSession` のリセット処理に足す（`InventoryManager.ReloadFromSave` が例）

### 新しいステージのシーンを作るとき
- `PlayerPartySpawner`、`PlayerSceneContext`、`PlayerSpawnPoint`（ID つき）、`DialogueSystem.prefab`、`Fps` を置く
- Build Settings に追加する（`[SceneName]` のドロップダウンの候補になる）
- `Tools > シーンチェック` で、遷移先・出現位置 ID・セーブキーの重複などを確認する
